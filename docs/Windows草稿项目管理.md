# Windows 草稿流程项目管理

本文件按项目管理原则维护目标、范围、基线、问题、风险、变更与验收；不是 PMP 认证或对外部服务可用性的承诺。Windows 与 Mac 分别记录构建、安装和验证，不能互相推定。历史发布、标签、工件和回执保持原样；版本规则以[版本管理](版本管理.md)为准。

## 目标与范围

作者能够在 Windows 工作台选择正式章节、连接现有 Chrome、只读检查差异，在明确确认后将内容保存为平台草稿并回读。不得自动提交审核、发布、定时或重放结果未知的写入。本轮用户授权只读验证，未授权实际平台写入。

## 工作方式与 GitHub

1. 每项工作先登记需求、范围、已知约束和验收标准；重大异常登记事实、影响、根因、修复、验证及回退。未证实的原因标记待查，见[故障复盘](Windows草稿连接故障复盘.md)。
2. 开始修改前识别并保留现有未提交工作；从核对过的基线建立 `codex/` 前缀分支或隔离工作树，按实际改动形成可审查提交。不得把未经确认的既有修改混入提交，不得覆盖历史标签和附件。
3. GitHub 的 issue、分支、提交、PR、CI、标签和 Release 分别对应问题、开发、变更记录、审查、自动验证、发布源码和发布工件；本地记录不能冒充已经创建或通过的 GitHub 对象。合并、正式发布及对外写入按用户授权和项目规则进行。
4. 发布前登记核心和 Windows 客户端各自的版本决策、来源提交、工作区差异、平台、工件及 SHA-256；按[版本管理](版本管理.md)和[发布维护说明](github-release.md)执行。Mac 未构建时明确标记未构建。
5. 分别登记开发、测试、构建、安装、运行和平台验收。安装前确认页面状态并备份作者数据；更新后核对实际运行文件。Windows 桌面或依赖改动按项目约束进行源码、发布目录和安装目录禁用技术扫描。
6. 已知故障必须有针对性回归；每次候选重跑相关历史回归和本次变更测试。测试通过不代替实际 Chrome 授权、只读检查或最终回读验收。回退保留候选、旧安装和作者备份，不更改历史凭据。

## 变更记录模板

每条记录包含：编号、日期和操作者；需求与范围；修改前状态及成功版本；问题是否曾出现（证据范围）；修改文件和配置；根因与证据；备份和回退；测试命令及结果；构建、安装、运行与平台验收状态；残留风险。记录按事实追加，不将未验证的推测写成结论。
