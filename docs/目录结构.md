# 技能源码、安装副本与小说目录

当前发布版 **v0.6.2** 包含 8 个技能、39 个载荷文件，支持本地三栏阅读与候选稿编辑。[发布记录](releases/v0.6.2.md)列出实际验证范围；本机安装不会自动更新。升级前备份书库及本地技能修改，保持八目录版本一致。

发布准备能力始于 v0.5.11；当前源码以同级 `story-skill-publish/`（`SKILL.md`、`agents/openai.yaml`、`LICENSE`）及核心共享模块 `story_publish.py` 提供。v0.6.0 核心运行时为 6 个 Python 文件；v0.6.1 起增加 `story_workbench.py` 后为 7 个。发布准备在目标书根保存独立 `.story/publishing.sqlite3`，按需生成 `.story/publishing-backups/` 账本备份和 `.story/publishing-exports/` 离线 ZIP 与包外回执，不写入剧情事件流。下方展示 v0.6.2 的八目录源码；安装时必须保持八个目录版本一致，不能把新核心与旧模块混装。[离线发布准备范围](platform-publishing.md)

v0.5.6 沿用 v0.5.3 的新书默认书名目录规则、7 个技能入口、33 个载荷文件及大纲分层、逐章细纲与历史归档，正文仍按带卷名的目录和带章名的文件保存。七入口拆分和源码移到仓库 `skills/` 始于 v0.4.0，具名分卷始于 v0.5.0；旧章路径继续兼容。[v0.5.6 版本说明](releases/v0.5.6.md) 与 [安装发布记录](github-release.md) 说明版本和平台范围。v0.5.10 的 Windows 导出修复已通过当版原生 CI，实际安装与验证范围以 [INSTALL.md](../INSTALL.md) 和[本版说明](releases/v0.5.10.md)为准。以下路径用 macOS 举例。

下文大纲分层、当前入口、历史归档和规划同步约定始于 v0.5.2；v0.5.3 加入默认书名目录规则。v0.5.6 统一了 `作品分析/` 的示例名称，并新增 `00_项目策划/` 默认落点；已有等效目录继续沿用。v0.5.6 的实际发布与核验状态见 [本版记录](../benchmarks/results/v0.5.6/README.md)；历史固定标签与附件未更名；测量数值保留，但记录中的名称已遮盖。实际默认安装按 [INSTALL.md](../INSTALL.md)，本机已安装技能不会自动更新。

## 三个层次各放什么

| 层次 | 路径示例 | 保存的内容 | 不放什么 |
|---|---|---|---|
| 技能源码 | `/Users/作者/Documents/GitHub/story-skill/skills/` | 技能入口、流程、共享运行时代码 | 某本小说的正文、状态、私有素材 |
| 项目安装副本 | `/Users/作者/小说/写作项目/.agents/skills/` | 从同一版本复制的 8 个技能目录 | 本书的设定、大纲与章稿 |
| 用户级安装副本 | 由当前应用的安装器确定实际技能目录 | 用户范围安装的技能，其他环境核对实际安装目录 | 源码维护改动和小说稿件 |
| 一本书 | `/Users/作者/小说/写作项目/新书/` | 创作约定、设定、正文和恢复状态 | 技能源码、其他书的状态 |

项目根和书根可以相同，也可以让一个写作项目包含多本书。每次操作都显式指定目标书目录；技能安装父目录不决定本次写哪本书。

story-skill/
├── skills/
│   ├── story-skill/
│   │   ├── SKILL.md                  # 总入口、任务路由、共同约束
│   │   ├── agents/openai.yaml        # 助手 发现元数据
│   │   ├── references/
│   │   │   └── project-state.md      # 共享卡片与章节计划
│   │   ├── scripts/
│   │   │   ├── story.py             # 唯一 CLI 入口
│   │   │   ├── story_storage.py     # 存储与恢复能力
│   │   │   ├── story_search.py      # 检索能力
│   │   │   ├── story_world.py       # 结构化世界状态
│   │   │   ├── story_history.py     # 历史修订分支
│   │   │   ├── story_publish.py     # 离线发布准备与本地核对
│   │   │   └── story_workbench.py   # 候选版本地只读快照与静态页
│   │   └── LICENSE
│   ├── story-skill-plan/            # 开书、设定、大纲、导入基线
│   ├── story-skill-write/           # 正文与续写
│   │   └── references/
│   │       ├── chapter.md          # 单章写作、审查与提交
│   │       ├── drama.md            # 中文冲突、看点、对白与场景
│   │       └── long-form.md        # 多线连载与世界状态
│   ├── story-skill-analyze/         # 深读、分析修订与证据
│   │   └── references/
│   │       ├── deep-reading.md     # 深读论证、跨文回读与解释边界
│   │       └── examples.md         # 按需读取的分析对照
│   ├── story-skill-review/          # 审稿与修订
│   │   └── references/history.md   # 历史分支、迁移与恢复
│   ├── story-skill-research/        # 扫榜与资料查证
│   ├── story-skill-cover/           # 封面
│   └── story-skill-publish/         # 离线发布材料与复核
├── scripts/                        # 开发、安装、探针、打包、同步
├── tests/                          # 软件测试与回归检查
├── examples/                       # 可公开的验证样例
├── docs/                           # 使用说明与工程文档

所有 8 个技能都有自己的 `SKILL.md`、`agents/openai.yaml` 和 `LICENSE`，上图省略了重复项。`SKILL.md` 说明何时使用及下一步读取什么；`references/` 仅在需要时读取，不要求每次加载全部内容；`agents/openai.yaml` 是发现元数据，不是另外一组执行代理。

v0.6.0 核心 `scripts/` 的 6 个 Python 文件必须一起保留；v0.6.2则是 7 个，增加 `story_workbench.py`。`story.py` 会从同目录加载其余模块，不把某个模块单独搬入其他技能，也不把候选核心与发布版其余文件混装。专用技能不复制运行时；发布准备使用本书独立的本地账本，不改变小说书库 schema 2。

| 技能 | 输入与工作边界 | 主要结果 |
|---|---|---|
| `story-skill` | 不确定入口、通用约束、断点与状态定位 | 路由到所需流程，提供共享工具 |
| `story-skill-plan` | 新书规划、设定、分卷、细纲、已有小说接入 | 创作约定、近期计划和有证据的导入基线 |
| `story-skill-write` | 已授权的长短篇正文与续写 | 章稿、审查记录、状态变化及下一断点 |
| `story-skill-analyze` | 明确来源与范围的参考小说、已有分析稿 | 开篇点评、可恢复深读、引文证据与独立修订稿 |
| `story-skill-review` | 指定正文与修改要求 | 问题清单、最小修改、外部改稿对账或历史候选 |
| `story-skill-research` | 当前创作决策需要的榜单或事实 | 带来源、日期与限制的研究结果 |
| `story-skill-cover` | 书名、署名、题材与上传要求 | 封面方案及可用图片工具生成的实际产物 |
| `story-skill-publish` | 已审查正式章与明确的平台目标 | 本地清单、离线材料包、包外回执及作者副本核对；不上传平台 |

例如，先用 plan 做分卷与前三章细纲，授权正文后转 write；只审小说正文用 review；学习参考书或修订分析稿用 analyze。切换技能只改变当前流程，同一本书的事实和断点仍保存在同一书目录。

## 安装：八个目录保持同级

```text
/Users/作者/小说/写作项目/
└── .agents/
    └── skills/
        ├── story-skill/
        ├── story-skill-plan/
        ├── story-skill-write/
        ├── story-skill-analyze/
        ├── story-skill-review/
        ├── story-skill-research/
        ├── story-skill-cover/
        └── story-skill-publish/
```

7 个专用技能通过同级 `story-skill` 找到共同约束和运行时。因此安装时保留目录名和相对关系；不要将专用技能放进核心内部，也不要把核心放到另一个安装父目录。

取得 v0.6.0 固定标签并按 [统一安装指引](../INSTALL.md) 核验 Release 附件与回下载结果后，可用同版项目安装器；未满足时仅在隔离项目核验本地源码：

```bash
python3 -B -X utf8 scripts/install.py --project "/Users/作者/小说/写作项目"
```

取得上述已核验源码后也要执行这一步；源码目录 `skills/` 与 助手 项目发现目录 `.agents/skills/` 已分开。想在仓库内调试，目标使用 `--project "."`，再按同一安装器更新副本。

仅缺核心时，从相同版本补装 `skills/story-skill` 到已有 7 个技能所在的父目录。多项缺失或版本不一致时按 [安装与升级说明](github-release.md) 核对整套。官方安装器拒绝覆盖已有同名目录；项目安装器的 `--update` 则要求原安装带有其托管清单且没有本地改动。改用另一种安装方式时，把旧版和本地修改备份到技能扫描目录之外，再核对新安装。

## 小说：一书一目录，状态与可见稿件分开

新书的最外层默认以实际书名命名，例如 `写作项目/雾港来信/`。先区分写作父目录与最终书根：只给父目录时新建书名子目录；用户明确指定最终书目录或已有作品时沿用，不能重复嵌套同名目录。未定名时采用并注明暂定书名。约定、策划、大纲、正文与状态都放在该书根中，完成时提供实际路径。

`init --book "<写作父目录>/<书名>" --title "<书名>" --kind long` 原样使用 `--book` 作为最终书根，`--title` 只登记标题，不自动追加目录。核对 `init` 回执的 `created/title` 和实际目录后，再保存创作约定与规划。v0.5.3 将默认选根规则纳入技能，不改变 CLI 的路径含义；已有误放在父目录的书须另行核对和整理，不用重新初始化掩盖原文件落点。

从参考作品开始时，只给写作父目录则默认将拆书材料保存到 `作品分析/<参考书名>/`，原创书仍放在自己的书名目录。用户另有分析目录或已有 `拆文/` 等目录时沿用。把已提炼方法写入原创规划时，重新建立人物、关系和事件，不将参考剧情登记成新书事实。完整流程见 [从拆书开始，新起一本书](../README.md#从拆书开始新起一本书)。

```text
/Users/作者/小说/写作项目/
├── .agents/skills/                 # 一份套件服务该项目
├── 作品分析/
│   └── 参考书名/                   # 独立分析根
│       └── .story/analysis/来源ID/report.md
├── 雾港来信/                       # 书名目录，--book 指向这里
│   ├── 创作约定.md                # 本书范围、风格、授权阶段和下一动作
│   ├── 00_项目策划/               # 按需保存，不创建空目录
│   │   ├── 开书策划.md
│   │   ├── 参考方法与原创重建.md  # 从拆书开书时保存
│   │   └── 设定.md                # 需要独立设定文件时
│   ├── 01_大纲细纲/               # 当前规划，沿用已有等效目录
│   │   ├── 全书总纲.md
│   │   ├── 第一卷 雨夜/
│   │   │   ├── 本卷大纲.md
│   │   │   ├── 第1章 雨中来客.md # 章细纲，正文在 chapters/
│   │   │   └── 第2章 一封旧信.md
│   │   └── 99_历史版本/             # 按日期或版本保留旧稿
│   ├── chapters/
│   │   ├── 第一卷 雨夜/
│   │   │   ├── 第1章 雨中来客.md  # 可阅读的正文导出
│   │   │   └── 第2章 一封旧信.md
│   │   └── 第二卷 归途/
│   │       └── 第3章 再过渡口.md
│   └── .story/
│       ├── state.sqlite3          # 正文、计划、状态、事件与审查记录
│       ├── drafts/                # 草稿及本次提交所需材料
│       └── workbench/             # 候选版派生静态页与备份，须被 Git 忽略
└── 短篇乙/                         # 另一书根，独立状态
```

分析稿定稿后的修订放在 `.story/` 外，默认可在分析目录内另建 `修订稿/` 并在稿件旁保留进度；只有外部分析文档时无需建立 `.story/`。旧报告路径不能代表独立修订稿的状态。[分析恢复方式](recovery.md#分析稿修订与续跑)

v0.5.11 的 `publish-export --book "<绝对书根>" --id "<清单ID>"` 在本书 `.story/publishing-exports/` 下生成一对 `material-<UUID>.zip` 和 `material-<UUID>.receipt.json`；文件名仅使用工具生成的 UUID。包外回执记录书籍与清单 ID、同名 ZIP 名称、原始 SHA-256、字节数和导出时间，命令返回 `export.receipt_path`。每次导出都是新的一对文件，不覆盖旧包。ZIP 内逐章分开保存标题、正文与作者的话，并附使用说明、目录、完整清单和本地核对记录；“作者的话”仅是候选字段，实际平台栏位须核对。材料包不代替书库备份或短篇全文，继续改稿也不会自动更新或撤销旧 ZIP。[材料包内容与条件](platform-publishing.md#离线材料包)

换会话后先用 `publish-list --book "<绝对书根>"` 找清单，再用 `publish-export-list --book "<绝对书根>" --id "<清单ID>" --offset 0 --limit 10` 分页找该清单的回执；列表只说明本书有哪些回执及对应 ZIP 是否存在，不核对当前稿，也不自动挑选最新包。选定后运行 `publish-verify-export --book "<绝对书根>" --receipt "<回执绝对路径>"`，或沿用 `--file "<ZIP绝对路径>" --id "<预期清单ID>" --sha256 "<原始SHA-256>"` 显式参数。工具只读核对包与当前正式稿，均通过后才可在平台身份与实际栏位核实后考虑人工填写。包外回执与 ZIP 同在本地，用于减少拿错包并发现意外损坏；它不是签名或平台回执，不能证明人为同时改写的两份文件仍有独立身份。回执缺失或损坏时从仍有效的清单重新导出。已取消、过期或来源变化的包只作历史存档；需要持久记录过期状态时另用 `publish-check`。

这里只展示主要目录；工具会按操作创建来源快照、分析导出和恢复备份等材料。新书需要独立策划或设定文件时，默认放在 `00_项目策划/`；已有书根下的同类文件和等效目录继续沿用，不为改名搬迁。方法文档保留分析来源与覆盖范围、适用条件、风险和新书中的具体改造，并指向承接它的策划或大纲。设定与大纲按需求建立，不为凑目录生成空文件。资料研究和封面产物保存在本次指定的书目录内，使用能说明内容的名称。

长篇先有从开端到结局的全书走向和分卷粗纲，再展开近期章节。全书总纲链接已建立的卷纲，本卷大纲链接已建立的章细纲；卷目录使用 `第X卷 卷名`，每章细纲使用 `第N章 章节名称.md`，一章一文件。短篇规划可以合为一份；用户已有等效布局继续沿用，不为目录补空章或提前细化整本书。

v0.5.10 起，长篇、短篇的现行全书大纲（短篇可用等效规划）都在靠前位置记录篇幅类型、目标平台和按该平台实际栏目填写的分类标签，并注明选择依据、来源日期及拟选／已确认状态。多个目标平台分别记录；未核实选项明示待核对，不把参考作品或其他平台的标签当成本书已确认分类。[具体字段](../skills/story-skill/references/project-state.md#大纲中的作品类型与平台分类)

同一范围只保留一个清晰的当前入口，文档头注明真实状态和更新时间；候选是否采用依据用户约定与任务记录，不能因整理而自动确认。后续分批设计更新相同文件，场面设计归入相应章；旧版本归档到 `99_历史版本/`，保留原文件名、来源和相对关系，避免多个版本、重叠章节范围并排充当当前稿。整理旧书先备份、核对各版、保留有效内容并修复引用；存在分歧时注明待定。普通修改细纲和整理旧稿时，都核对并同步已采用的工具计划；续写前定点核对本章当前入口。未决候选不能覆盖已采用计划，已有采用依据不重复确认；不改已发生的正文事实或搬动托管正文。完整规则见 [项目状态与规划](../skills/story-skill/references/project-state.md#可读的大纲与细纲)。

正文在 `chapters/` 下按分卷建目录，卷目录名固定为 `第X卷 卷名`，例如 `第一卷 雨夜`、`第二卷 归途`，卷序号与卷名之间一个空格。短篇与单卷作品也须明确首卷名称。每章文件名固定为 `第N章 章节名称.md`，N 是不补零的阿拉伯章号，章号与章名之间一个空格。

v0.5.10 的短篇完本交付在书根另生成 `<书名>.txt`，按章号顺序合并所有已提交章节；`chapters/` 的逐章文件保留。首次运行 `assemble-short --book "<书根>" --final-chapter N` 确认实际最终章号并将全文登记为受保护导出。之后正式修订、对账、历史发布或新增章节会随导出刷新已有全文，包含当前全部连续已提交章节。交付前核对 `status.short_assembly` 与导出回执，缺失或待导出时用 `export` 恢复，外部改动先保留并解决冲突。全文同步状态和已合并章数不证明情节完结，确认完本仍须核对实际终章、结局与全文。

短篇的 `init`／`status` 回执另有 `short_assembly_path`，首次合并前给出预期相对路径，登记后给出实际路径。普通书名保持 `<书名>.txt`；特殊字符会替换，必要时截短并保留可区分后缀，完整书名仍保留在元数据中。新合并稿从第 1 章章名起，仅含章名和正文；旧的含书名首行合并稿在只读状态中标为 stale，下次执行 `export` 或明确重组时备份旧版并刷新。刷新与恢复沿用已登记路径，不自动覆盖同名不明文件。通过 `adopt` 接入的旧短篇在原目录只读的前提下，按 [旧短篇补齐原章](../skills/story-skill/references/project-state.md#旧短篇补齐原章) 用 `adopt-backfill` 补存真实缺章，再完成合并。

短篇完本交付还需有实际封面图片；优先沿用书内已有封面目录，新书可用 `04_封面/`。封面与全文均保存在本书根内，交付时分别给出可打开的路径。首次完本核对封面的书名、已有署名和实际尺寸；后续正式修订仅在书名、署名、题材或投稿规格变化时复核或修订封面。仅审稿不生成或更新完本产物，封面方案或提示词不能代替图片文件。

明确要求完本交付时，同步核对现行总纲或短篇等效规划的篇幅类型、目标平台、原生分类标签、终稿内容依据、来源日期及拟选／已确认／待核对状态；缺漏或不符时保留旧版并按 [分类字段](../skills/story-skill/references/project-state.md#大纲中的作品类型与平台分类) 补齐，不静默更改平台已确认值。旧短篇正式修订后要求完整成品，即使此前未合并，也按 [完本流程](../skills/story-skill-write/references/chapter.md#短篇完本与修订交付) 首次交付全文、实际封面和总纲分类。普通单章修订只核对已有全文同步，纯审稿或候选稿不自动生成首次成品，不每章重复查平台。

章计划 `volume_dir` 指定完整分卷目录名，显式填写时优先使用；未填写但计划已有 `volume` 时，可沿用该 ID 已保存且带卷名的目录，或采用已符合 `第X卷 卷名` 格式的世界卷记录标题，工具会保存本次选择；同一个 `volume` ID 已绑定的目录不能被后续单章计划静默覆盖，填写冲突目录会被拒绝。缺少完整卷名时先核对已有分卷规划；尚未命名时，依据已授权的本卷内容拟定卷名后再提交，不用仅有卷号或内部 ID 的目录代替卷名。`title` 指定章节名称，未填写时从草稿首行纯文本 `第N章 章节名称` 提取并去掉原章号前缀，旧版 Markdown H1 仍可读取。新写章须提供章名，无标题的导入基线可用章名 `正文`，但仍须明确所属卷名：`adopt --volume-dir "第一卷 雨夜"` 可直接指定（替换为本书实际卷名），也可从已保存的该章计划取得完整目录；仅指定导入卷名无需新建章计划。结构化计划的 `volume` 仍是世界状态稳定 ID，展示目录用 `volume_dir` 指定。卷内约束的 `scope: "volume:v1"` 须对应计划的 `volume: "v1"`，或将约束卡显式加入 `requires`；目录名不会自动建立此关联。

新章节采用此布局；已有工程的旧正文路径仍可识别，更新技能不会批量重命名或移动旧稿。实际文件位置以提交、导出或对账回执为准；历史分支可用 `history-inspect` 的分页 `affected[].path` 查当前正文路径，不根据章号拼接旧式数字文件名。

`chapters/` 用于阅读和交付，`.story/` 保证状态与恢复。只复制 `chapters/` 可以交付正文，不能当作完整书籍备份。备份时等待工具退出，再复制整本书目录；直接改过导出正文，下一次先对账，不能让旧数据库静默覆盖新稿。[恢复指南](recovery.md)

v0.6.2使用 `.story/workbench/index.html` 保存每本书的派生只读页面，并可能在 `.story/workbench/.backups/` 保留被替换的旧页面。它不是正文、状态库或发布回执，重建页面不会改变权威书稿。书目录若属于 Git 仓库，必须忽略整个 `.story/workbench/`，且不能跟踪其中旧文件；只忽略 `index.html` 不足以覆盖备份。工作台当前只显示概览和本次章节页，其他分区仍是摘要；草稿、候选稿、大纲和封面未登记时不会靠目录猜测。[工作台说明](本地工作台分析.md)

不要在技能目录存放小说正文，也不要把多本书共用成一个 `.story/state.sqlite3`。运行核心 CLI 的书籍命令时始终明确 `--book`；`template` 与帮助命令不附该参数。例如：

```bash
python3 "/Users/作者/小说/写作项目/.agents/skills/story-skill/scripts/story.py" status --book "/Users/作者/小说/写作项目/雾港来信"
```

## 改动与发布的落点

技能行为或说明应在仓库 `skills/` 中修改；安装、打包和验收工具应在仓库根 `scripts/` 中修改；某本书的内容应在该书目录中修改。技能更新不会自动导入、迁移或重写书稿。

根 `.agents/skills/` 的安装副本和 `dist/` 构建产物不提交 Git；可公开的样例、稿件交付、文档与 benchmark 不因为这次目录整理而被整体忽略。v0.3.0 的固定 tag、附件和历史报告保留旧事实，新版以新布局重新验证后再发布。
