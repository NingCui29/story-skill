# 版本号与更新规则

本规则适用于技能套件、各宿主分发包、Python 作品服务、浏览器工作台及 Mac／Windows 客户端。统一采用“变更影响决定升哪一位，实际交付内容决定哪些端升版”。规则自 2026-10-27 起用于后续版本决策；现有开发版本、已发布标签、附件及历史回执不追溯改号。本次规则整理本身不升级运行时或客户端。

## 递增原则

产品版本使用三段数字 `MAJOR.MINOR.PATCH`，按数字逐段比较，不按字符串或发布日期比较。同一发布批次按影响最大的变更定级，不按提交次数、修改文件数或开发天数升版。

| 变更影响 | 递增方式 | 示例 |
|---|---|---|
| 修复问题、性能优化、兼容的小调整，保持既定使用方式 | PATCH 加一 | `0.6.29 → 0.6.30` |
| 增加明确的用户能力、完整模块或工作流，保持已有能力兼容 | MINOR 加一，PATCH 归零 | `0.6.29 → 0.7.0` |
| 稳定版中破坏已有接口、数据兼容或使用约定 | MAJOR 加一，MINOR／PATCH 归零 | `1.4.2 → 2.0.0` |

`0.x` 阶段也按修复和新增能力区分 PATCH／MINOR；不兼容变更至少升 MINOR，并写明影响、备份和迁移办法。`1.0.0` 表示开始承诺稳定兼容，由兼容与验收条件决定。进入稳定版后，不兼容变更必须升 MAJOR。内部重构本身不决定版本级别，以实际对外影响为准。

开发过程中的多次修改可以归入同一待发布版本；已经有开发编号的工作继续保留其身份，发布前对尚未分发的新版本统一定级。仅修改仓库维护文档、测试或验证记录，且不改变分发内容时，无需升级产品版本；技能规则、随包说明和包装脚本的变化若改变交付内容，仍须按影响定级。

## 各端版本来源

| 部分 | 权威来源与同步要求 |
|---|---|
| 技能套件、Python 作品服务、浏览器工作台 | 以 [story.py](../skills/story-skill/scripts/story.py) 的 `VERSION` 为准，浏览器界面不另建产品版本线 |
| Codex、DSH、Claude、npm 分发 | 与套件同号；[Codex 元数据](../.codex-plugin/plugin.json)和 [DSH 元数据](../dsh/package.json)必须同步，Claude／npm 从实际载荷读取版本；各宿主目录安装保持完整同版套件 |
| Mac 客户端 | [Info.plist](../desktop/macos/Info.plist) 的 `CFBundleShortVersionString` 是独立客户端版本，`CFBundleVersion` 是构建号 |
| Windows 客户端 | [项目配置](../desktop/windows/StoryWorkbench/StoryWorkbench.csproj)的 `Version` 是独立客户端版本；`AssemblyVersion`／`FileVersion` 同步为 `X.Y.Z.0`；[MainWindow](../desktop/windows/StoryWorkbench/MainWindow.cs) 与 [UpdateService](../desktop/windows/StoryWorkbench/UpdateService.cs) 的 `ClientVersion` 常量保持一致 |
| 作品数据库 | `story.py` 的 `SCHEMA_VERSION` 单独管理；仅在存储结构或读取约定需要变化时递增，并提供兼容或迁移措施 |

各端无需同时发布或使用相同数字。只调整技能规则且不重新交付桌面包时，桌面版本保持原样；桌面交付包含原生宿主、共享界面或内置服务的变化时，客户端必须独立升版，级别取决于该端实际获得的变化。只升级内置 Python 服务也适用。

Mac 正式重新分发有变化的应用时，同时提高三段客户端版本和 build；build 持续递增，不随产品版本归零，也不要求与 PATCH 保持固定算术关系。当前更新器不比较 build，不能只升 build 来发布更新。未发布候选可重复构建，但须记录源码、构建标识及摘要；从已验收候选转正式发布且包体未变时，沿用该候选身份，无需再改号。

Claude 默认文件名中的 `r2` 来自 [BUNDLE_REVISION](../scripts/package_claude.py)，表示包装格式修订，不是构建次数，也不代替套件版本。后续包装修复若改变交付内容，使用新的统一套件版本；现有默认 `-r2`、历史不带后缀的正式附件名及旧版更正记录保留原样。

## 开发、发布与更新通道

开发中、候选已构建、验收通过、正式发布、已安装、服务已加载是不同状态，分别记录。版本号或打包成功不能证明已发布、已安装或运行中的服务已更新。当前安装副本和运行中的服务应按实际文件、来源及运行状态核对。

当前安装器和更新器使用三段数字版本；开发／候选状态记录在文档与构建回执中，不直接加入未经工具支持的 `-dev`、`-rc` 或 `+build` 后缀。候选重复构建应登记各次摘要，同一个版本号不足以证明文件相同。

主发行使用 `v<套件版本>`，Windows 独立发行使用 `windows-v<客户端版本>`；Windows 独立发行不占用主发行的 latest。Mac 当前从主发行的 latest 附件中按架构及客户端版本查找安装包，Windows 从正式 `windows-v*` 发行列表查找。Mac 还没有独立发行通道；主发行未附适用 Mac 包时，当前 Mac 更新器会提示不可用，用户需使用 [Mac 说明](../desktop/macos/README.md)中的固定下载链接。规划新的通道不能写成已经实现。

不同端的安装包分别记录客户端版本、内置 Story Skill 版本、源码来源、构建来源、平台／架构、文件清单及 SHA256。未重建的端继续登记其原内置版本，不能用新的套件号替换旧包的记录。

正式发布后的标签、各形态附件及已登记摘要保持固定。同一套件版本可有标准包、插件包和不同平台包，各形态分别核对内容；不得用不同内容覆盖同一正式附件或注册表版本。修复后使用新版本发布，原问题和撤下原因另行记录。发布记录可以补充真实验证结果，不能改写原构建来源或旧结论。

## 每次更新的执行顺序

1. 列出对用户的变化、兼容性影响和实际交付的端，按最高影响确定本批次各端的版本级别。
2. 从各自权威来源更新版本，核对宿主元数据、Windows 常量、Mac build、版本化载荷白名单与对应打包验证规则；保留旧版清单。
3. 构建实际要交付的包，登记源码提交和工作区差异、客户端／内置服务版本、平台、清单及摘要。各端范围按实际清单记录，不固定沿用旧版附件数量。
4. 执行适合本轮变更的检查。涉及依赖或桌面变更时运行 `python scripts/check_forbidden_technologies.py --source`；Windows 构建还须对完整发布及安装目录分别执行 `--root <目录>`。原生执行、宿主加载和平台实页验收分别记录，不能由源码检查代替。
5. 同步 README、INSTALL、相关桌面说明和发布记录中的版本、状态、兼容性与固定下载地址；主发行未重建的端继续指向原正式包，明确更新发现限制。
6. 正式发布时核对标签、附件名、实际载荷版本、校验文件及 npm 版本的一致性，并按实际结果登记回下载。安装和服务重启仍按原授权及[工作台更新流程](工作台更新流程.md)执行。

具体打包和发布步骤见[发布维护说明](github-release.md)，技术与数据兼容边界见[技术约束](技术约束.md)。
