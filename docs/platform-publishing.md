# 七猫、番茄章节发布接入方案

状态：**v0.5.11 开发源码实现阶段 A 的离线准备和 B0 的作者副本本地核对；平台上传与发布尚未实现**。核对日期：2026-09-23。设计基线：v0.5.10，提交 `607d3e3`。开发套件增加为八个技能，仍未发布或升级本机安装；下文远端流程属于后续设计。

这里的“发布账本”是每本书 `.story/publishing.sqlite3` 中的**本地准备记录**，与小说创作状态分开。它保存准备投向哪个平台和作品、选了哪些正式章节、冻结内容及校验依据，以及清单是否仍可用于人工交接；明确要求留痕时，还保存作者副本的本地比较摘要。账本不登录作家后台，不保存密码或 Cookie；平台账号／作品 ID 只是用户声明，账本里的记录不能证明平台已收稿、审核或上线。

## 已实现的离线命令

从开发源码使用 [story-codex-publish](../skills/story-codex-publish/SKILL.md)，命令入口仍是 `story-codex/scripts/story.py`。正式章节的准备、清单记录、ZIP 导出、材料包复核及备份不联网，不递增创作 revision，不写剧情事件。当前仅支持 `mode=draft`，目标账号和作品 ID 均是用户声明，尚未经过平台核验。

| 命令 | 已实现范围 |
|---|---|
| `template publish` | 输出平台、账号 ID、作品 ID、连续章号列表及 draft 模式的输入结构 |
| `publish-prepare --book "<绝对书根>" --input "<JSON路径>" --expect R --summary` | 严格核对导出、当前正式版本及审查记录，保存完整快照并返回简洁回执；省略 `--summary` 返回全文；相同有效清单幂等复用 |
| `publish-list --book "<绝对书根>" --offset 0 --limit 10` | 分页列出清单摘要；没有账本时查询不会创建它 |
| `publish-inspect --book "<绝对书根>" --id "<ID>"` | 回读完整冻结清单；预算不足明确报错，可增加 `--budget-bytes` |
| `publish-inspect --book "<绝对书根>" --id "<ID>" --summary --offset 0 --limit 20` | 分页查看章号、章名、字数、路径与内容摘要；没有正文，以 `chapter_page.next_offset` 续页 |
| `publish-inspect --book "<绝对书根>" --id "<ID>" --chapter N` | 返回一章的完整冻结内容及来源证明；不在清单中的章号明确报错 |
| `publish-check --book "<绝对书根>" --id "<ID>"` | 重新核对当前正式版本和导出，返回各章差异与本次创作 revision；stale 刷新差异但不复活，cancelled 跳过检查 |
| `publish-export --book "<绝对书根>" --id "<ID>"` | 重新核对正式稿，仅 prepared 且匹配时生成新的离线材料 ZIP 及同名包外回执；返回 `export_created`、`export.receipt_path`、ZIP 真实路径与 SHA-256，不覆盖旧包 |
| `publish-export-list --book "<绝对书根>" [--id "<ID>"] --offset 0 --limit 10` | 分页列出本书包外回执和对应 ZIP 是否存在；可按清单 ID 筛选，不核对当前稿，不自动选最新包 |
| `publish-verify-export --book "<绝对书根>" --receipt "<回执绝对路径>"` | 从包外回执读取原清单 ID、ZIP 路径与原始 SHA-256，只读核对包、所属书、原清单及当前正式稿 |
| `publish-verify-export --book "<绝对书根>" --file "<ZIP绝对路径>" --id "<预期清单ID>" --sha256 "<原始SHA-256>"` | 兼容原有显式参数方式；清单 ID 和 SHA-256 须来自原始导出回执，核对范围相同 |
| `publish-compare --book "<绝对书根>" --id "<ID>" --chapter N --input "<JSON路径>"` | 只读比较作者提供的后台回读副本与一章冻结内容，并核对当前正式稿；不访问平台、不保存或验证远端状态 |
| `publish-compare-record --book "<绝对书根>" --id "<ID>" --chapter N --input "<JSON路径>"` | 显式比较并在本地账本新增一条摘要记录，返回记录 ID；不保存正文或声明平台已保存 |
| `publish-compare-history --book "<绝对书根>" --id "<清单ID>" --offset 0 --limit 10` | 分页列出该清单的历史本地比较记录，不重新核对当前正式稿 |
| `publish-compare-inspect --book "<绝对书根>" --record-id "<记录ID>"` | 查看单条历史摘要及保存时判断，不把旧结果当作当前稿或平台状态 |
| `publish-cancel --book "<绝对书根>" --id "<ID>"` | 取消本地清单，不涉及平台上的任何稿件 |
| `publish-recover --book "<绝对书根>"` | 无需清单 ID 即可恢复未完成事务并校验清单；不改清单状态，账本不存在时不新建 |
| `publish-backup --book "<绝对书根>"` | 校验数据库结构、清单指纹和本地比较记录，建立独立备份；没有从备份自动覆盖现有账本的命令 |

所有清单均保留 `platform_verified=false`、`ready_to_upload=false`，远端状态为 unknown。`content_verification=unread` 专指远端上传正文尚未核验，本地回读、核对成功或 ZIP 导出都不会改变它。当前状态仅包括本地 prepared、stale、cancelled；下文 sending、平台回执、执行互斥和原生排期尚无对应执行器。逐章准备可用于长短篇，但不等于整篇投稿、完本审查或已取得远端发布授权。

清单列表、导出回执列表、回读、取消和恢复不隐式重新核对正式稿；`source_check_performed=false` 表示本次没有核对，带 `source_matches_current=null` 的回执也不能据此断言匹配。准备、检查、材料导出前的核对及材料包复核会报告本次正式稿匹配结果；其中材料包复核是只读操作，不修改账本中的状态或 `checked_at`。导出已取消清单仍跳过核对，不生成 ZIP。`checked_revision` 和 `chapter_checks` 分别说明本次检查的创作版本与各章差异。过期清单即使在恢复导出后再次匹配，也保持 stale，由新的显式准备生成可用清单。

批量材料可先取得简洁准备回执，再分页查看章目和按章回读。`content_scope` 区分 metadata、chapter_summaries、single_chapter 和 full_manifest，只有 full_manifest 包含全部章节正文；各视图均保留原清单 ID、完整指纹与冻结状态。`--summary` 与 `--chapter` 互斥，分页参数仅用于摘要；预算不足明确失败，不返回截断正文。

取消或过期的清单保留原 ID 和内容；新的显式准备请求可生成新 ID，仍有效的相同清单则幂等复用。无关笔记或未来规划造成的全局 revision 变化，不改变所选正式章节和目标时仍复用原清单，其准备 revision、全文与原始指纹均保持不变；本次确实重新核对来源时刷新 `checked_at`。全文指纹包含审计版本；复用判断仅排除全局 revision，不忽略正式 head、审查证明、路径、转换或目标变化。

首次建库先在临时文件完成事务，再安全放到正式路径。现有账本的未完成事务可能需要写连接恢复；查询返回 `publishing_recovery_required` 时，运行 `publish-recover --book "<绝对书根>"`，然后重新查询，无需先取得清单 ID。恢复检查账本及清单完整性，但不改变 prepared、stale 或 cancelled，不代替正式稿版本核对。这不是从备份覆盖恢复或完整断电容灾：POSIX 在首次发布的 link/unlink 极窄窗口中断后可能留下双链接，此时按路径防护拒绝继续，保留现场待核对，不能删库重建。

数据库连接核对实际打开的文件，而不仅是打开前后的路径。POSIX 通过 `/dev/fd` 与文件身份核对新增连接；本模块连接在同一进程内串行。若同进程其他 SQLite 客户端导致缓存句柄无法归属，返回 `publishing_connection_unverifiable`，关闭外部连接后重试；宿主没有可用句柄信息时也停止处理。Windows 使用禁止删除共享的原生句柄，在连接存续期间阻止主库路径被替换。Windows 分支仍需原生 CI 验证，不能从 macOS 用例推定通过。

清单不仅校验外层指纹，也校验所属书籍、非空连续章序、来源证明格式、冻结内容摘要及字数。旧开发账本即使标为 schema 1，若仍使用全局唯一指纹约束，也会返回 `publishing_schema_mismatch`；保留文件待单独迁移，不自动删除取消清单或改数据库版本。当前支持的 schema 1 旧清单继续可读，回读历史快照不要求其仍匹配当前正式稿。

## 离线材料包

已有清单可直接运行 `publish-export --book "<绝对书根>" --id "<清单ID>"`，无需用户填写新的 JSON。工具在导出前重新核对正式稿，只有清单状态为 prepared 且本次匹配才生成材料包；stale、cancelled 或正文存在外改时不生成。修复后仍须对 stale 清单显式重新准备，不能通过重复导出恢复其有效状态。

材料包位于书根 `.story/publishing-exports/material-<UUID>.zip`，旁边的 `material-<UUID>.receipt.json` 是包外原始回执，两个文件使用同一工具生成的 UUID。回执保存书籍 ID、清单 ID、同名 ZIP 文件名、ZIP 原始 SHA-256、字节数及导出时间；`publish-export` 返回其绝对路径 `export.receipt_path`。每次生成新包与新回执，不覆盖以前的文件。交付时核对 `export_created`，报告 ZIP 和包外回执的真实路径以及清单 ID、原始 SHA-256；保留两者供之后找回和验包。

```text
material-<UUID>.zip
├── 使用说明.txt
├── 目录.txt
├── manifest.json
├── receipt.json
└── 章节/
    └── 第N章/
        ├── 标题.txt
        ├── 正文.txt
        └── 作者的话.txt
material-<UUID>.receipt.json  （ZIP 外，与 ZIP 同目录）
```

`manifest.json` 保留完整冻结清单，ZIP 内的 `receipt.json` 保留本次本地核对记录，不能替代 ZIP 外同名 JSON 中保存的原始 SHA-256。各章的标题、正文和作者的话按冻结字段原样写为 UTF-8，保留已有换行和字符；作者的话为空时仍保留对应文件。`作者的话.txt` 仅是本地保留的候选字段，实际后台有无对应栏、名称和位置须按目标平台页面核对，不能假定番茄、七猫有相同输入栏位。包内没有平台上传或提交动作，短篇材料包也不等于短故事整篇投稿。

导出成功只证明导出时的正式稿与清单匹配，不增加创作 revision，也不改变远端状态或平台核验标志。此后继续改稿，需要重新核对或准备材料；已经导出的旧 ZIP 不会自动更新或撤销。材料包不是完整书库或发布账本备份，账本备份仍使用 `publish-backup`。

### 交付与再次使用材料包

1. 换会话时先用 `publish-list --book "<绝对书根>"` 确定清单 ID，再用 `publish-export-list --book "<绝对书根>" --id "<清单ID>" --offset 0 --limit 10` 分页找到该清单的各次导出回执。按回执和目标 ZIP 逐一选择，不以文件时间推断“最新包”可用。列表只索引本书回执及 ZIP 是否存在，不证明 ZIP 内容完整或当前正式稿匹配。单份损坏的回执计入 `invalid_total`，前 10 项路径及错误码列于 `invalid_receipts`；内容损坏不掩盖其他完整回执，不安全链接与目录换位仍整体拒绝。
2. 选定包外回执后运行 `publish-verify-export --book "<绝对书根>" --receipt "<回执绝对路径>"`。也可继续用 `--file "<ZIP绝对路径>" --id "<预期清单ID>" --sha256 "<原始SHA-256>"`，其中 ID 和 SHA-256 来自原始导出命令回执或新保存的包外回执，兼容旧包。工具要求新包的回执与本书、同名 ZIP 和原清单对应，比对包的原始哈希、成员与内容、来源证明、目录和使用说明，同时核对当前正式版本、审查证明、路径和导出健康；从待查 ZIP 内取得的 `receipt.json` 不能代替原始导出回执。
3. 分开检查 `artifact_verified` 与 `usable_now`。前者表示包与预期清单、原始哈希匹配且内容完整；后者只有清单仍为 prepared 且本次来源匹配时才为 true。`source_check_performed`、`source_matches_current` 和 `checked_revision` 说明本次正式稿检查及所查版本。包完整但清单已取消、过期或来源变化时，仍可作为历史存档，不能用于手工填报；包内导出时的 prepared 不能代替清单现在的状态。
4. 包外回执缺失或损坏时，从仍有效的清单重新导出并保留新回执。不要以刚读取的待查 ZIP 哈希冒充此前保存的校验值。回执与 ZIP 同在本地，可减少拿错包并发现意外损坏；若两者被人为同时改写，本地配对不足以提供独立身份认证。它不是数字签名、可信时间戳或平台回执。
5. 包完整且当前可用时，在平台页面确认实际登录账号、作品及章节位置，再按包中的字段填写。本地核对不会证明平台身份、接收结果或发布状态，也不会授予或执行平台操作。

材料包复核不修改发布账本的 `status`、`checked_at` 或创作 revision，也不把旧包内容收录为当前正文。需要把此次发现的过期状态持久记录到账本时，另运行 `publish-check --book "<绝对书根>" --id "<清单ID>"`。已取消或过期的包不因复核通过而恢复可用；修复后需显式重新准备、导出并复核。包损坏、所属书不符或原始清单无法核实时，应保留文件并处理具体问题，不能仅凭文件名或列表记录认定可用。仅核验存档时，无需自动重新准备或持久修改清单状态。

## 人工填写后的副本核对

作者自行在官方后台填写并保存草稿后，可以把后台可见的单章标题和正文复制到本地 JSON，以 `publish-compare --book "<绝对书根>" --id "<清单ID>" --chapter N --input "<JSON路径>"` 与冻结清单对照。`title`、`body` 必填；只有后台实际提供作者的话且作者能够回读时才附 `author_note`。输入保存在书根 `.story/` 的本地私有路径，不提交公开仓库，不包含密码、Cookie 或验证码。

命令逐字段比较，仅将 CRLF／CR 统一为 LF，保留其他空白、汉字、标点和段落差异；结果给出已核对字段、未核对字段及摘要，不把正文回显到终端。`copy_matches_frozen=true` 要求三个字段均有副本且全部匹配。`usable_now` 在这里仅表示该副本与仍有效的冻结清单及当前正式稿适合继续人工核对，**不**代表后台真的保存了这些内容。所有结果恒标记 `user_supplied_copy`、`platform_verified=false`、`ready_to_upload=false`、`remote_state=unknown`。用户自行提供的截图、复制文本或口头描述也不自动升级为工具直接取得的平台回执。

只需临时核对时继续使用只读的 `publish-compare`。需要跨会话留存时，显式运行 `publish-compare-record`，同一份 JSON 再比较一次并在发布账本中**新增**本地记录；失败或输出预算不足不会保存半条。记录包含书籍、清单和章节标识、清单指纹、UTC 保存时间、已核对字段、原始及换行统一后的摘要、各字段匹配和当时的正式稿核对结果，不保存复制来的正文、输入路径或平台登录资料。相同输入再次执行仍产生新记录，不覆盖前次历史。`record_id` 和 `record_sha256` 只用于找回与检查本地记录，不是平台回执、数字签名或可信时间戳。

中断后用 `publish-compare-history --book "<绝对书根>" --id "<清单ID>" --offset 0 --limit 10` 找到记录，再用 `publish-compare-inspect --book "<绝对书根>" --record-id "<记录ID>"` 查看。历史里的 `status_at_record`、`source_matches_current_at_record` 和 `usable_at_record` 只描述**保存当时**；历史查询不重新核对正式稿。之后改稿或取消清单，旧记录仍可读，但不能凭旧的 `usable_at_record=true` 继续填报，须用 `publish-check` 核对清单并重新取得作者副本。`publish-backup` 和 `publish-recover` 会校验并计数本地比较记录，旧的 schema 1 账本无须迁移。账本管理员仍可修改数据库，因此这些本地摘要不是独立防篡改证明。

| 实际账号能力 | 尚未登录作家后台实测 | 草稿、长篇章节、短故事投稿、排期、回读全文各自验证，不能互相推定支持 |

在本方案中，两家的自动化接入边界均标为 `blocked_pending_platform_permission`；当前离线账本不保存此远端能力状态。这不阻止作者在官方后台人工填写自己已核对的材料。官网规则以后可能变更，真正接入前须重新核对适用版本及许可范围。七猫上述协议还规定了 AI 生成内容标识。若投稿流程要求相关声明，按实际创作方式及平台要求填写，不预设“未使用 AI”或删除已有标识。多平台支持按作品签约范围启用，不默认同一本书可以双平台发布。

## 已有能力与新增边界

现有 [story.py](../skills/story-codex/scripts/story.py) 的 `commit`、`delivery`、`chapter_path` 可提供本地正式稿、导出结果和真实章节路径。[story_storage.py](../skills/story-codex/scripts/story_storage.py) 保存不可变正文对象；[story_history.py](../skills/story-codex/scripts/story_history.py) 管理正式版本及审查收据。

需要区分三件事：

- `exports_complete`、`full_book_verified` 反映本地导出和文件完整性，不证明语义审查通过，也不证明平台发布成功。
- `adopt`、`adopt-backfill` 的初始收据为 `imported_unverified`。导入章通过正式历史审查后仍可能保留 `imported=1`，发布资格必须依据当前正式版本及有效审查收据，不能仅凭导入标记放行或永久拒绝。
- `chapter-read --sha` 能读取历史候选；`history-publish` 是并入本地正式稿。读得到正文或命令名带有 publish，都不能当成远端发布证据。

开发源码已新增 `story-codex-publish` 和共享模块 `story_publish.py`，当前只实现前述离线命令。后续再按平台增加适配说明及执行器；普通提交、导出和导出重试不触发平台写入。

## 未来取得平台许可后的自动化流程设计

1. **准备清单。** 指定书、平台、章节范围和草稿／立即提交／定时提交方式。检查正式稿和审查资格，展示章序、标题、字数、目标作品及排期；生成可回看的固定内容。
2. **核对绑定。** 在账号会话中核对稳定的账号身份、平台作品 ID 和作品名称。只使用书名或当前浏览器页面不足以建立绑定。首版限定平台上已经创建的作品。
3. **执行已授权范围。** 先取得适用平台的接入许可，再按用户明确指定的整批范围执行；授权覆盖该批清单，无须每章重复确认。“继续分析”“继续写作”不自动获得平台发布授权；目标账号、作品、正文或提交方式超出范围时重新确认变化。
4. **回读与交付。** 逐章记录平台结果及核对程度。报告成功、驳回、待核实的具体章节，保留断点，不能把整批部分成功报告为全部成功。

登录、验证码或二次验证交由用户在平台界面完成，不收集密码、不导出浏览器 Cookie。账号切换后重新核对绑定。技能流程通过宿主支持的浏览器工具或官方授权接口执行；没有适用工具时仍可生成本地清单，但不能报告上传完成。

长篇章节与短故事整篇投稿分别建能力清单。短篇全文文件可作为投稿内容来源，但必须绑定所有构成章节的正式版本、全文合并记录和完本审查；不能把已合并直接当成已审查。远端整篇能力未验证前，不宣称短故事投稿可用。

## 内容、身份与状态记录

离线准备在书根建立独立的 `.story/publishing.sqlite3`，使用 schema 1。书籍创作库 schema 2 不因发布记录增加事件；现有历史重放遇到未知事件会失败。`publish-backup` 将账本中的完整清单快照和显式保存的本地比较记录一起备份；恢复目前须单独核对，不提供自动覆盖。未来加入远端操作后，本地创作回滚不能删除远端操作事实。下表的发送尝试、远端观察及授权执行记录属于后续接口设计。

| 记录 | 必要字段与约束 |
|---|---|
| 平台绑定 | 本地书 UUID、平台、账号稳定标识、远端作品 ID、绑定版本、核对来源和时间；书名是展示信息，不能替代身份 |
| 正式稿证明 | 章号、当前正式 head ID、正文 SHA、审查收据 SHA、准备时创作 revision、实际 `chapter_path`；整体 revision 用作审计，正式 head 和审查证明用来核对版本 |
| 上传快照 | 标题、完整正文、作者的话、来源证明、转换规则版本、实际上传内容 SHA；一经准备不可静默修改 |
| 发布计划与授权 | 快照 ID、绑定版本、操作类型、章节范围、排期时间和时区、用户指令依据；正文和发布选项都属于授权范围 |
| 发送尝试 | operation ID、attempt ID、发送前记录、执行阶段、结果、远端章节 ID、观察时间和证据；保留每次尝试，不能用新结果覆盖旧事实 |
| 远端观察 | 平台状态、内容核验结果、来源、观察时间、可见范围及平台原始状态；不存密码、令牌或 Cookie |

标题和正文的分栏转换必须可预览、可追溯。只按明确规则移出已经确认的章头，保留正文首段、对话、空行和中文标点；不以“清洗 Markdown”为由删改作品内容。平台字段若自带章序，按实际字段拆分，避免重复出现“第 N 章”。字数采用平台实际口径，不假设等于本地 `visible_nonspace_v1`。

全量回读若只发生换行等平台标准化，可按已记录的比较规则核对，并保留原始上传值及原始回读值。不得去除全部空白、标点或截断正文后计算一个“相同”哈希。

执行状态与平台事实分开记录：

| 层面 | 拟记录的值 | 含义 |
|---|---|---|
| 本地执行 | prepared、stale、sending、observed、unknown、blocked、cancelled | 清单待执行、版本过期、正在发送、有回执、结果不明、阻断、未发送前取消 |
| 平台状态 | draft、scheduled、in_review、live、rejected、removed、unknown | 仅依据平台观察映射，不假设各平台都有全部状态或按同一顺序变化 |
| 内容核验 | full_match、mismatch、partial、unread | 独立于平台状态；后台显示“已发布”但只读到标题时，全文仍为未核验 |

`observed` 只表示取得平台证据，不等于已上线。轮询读取失败保留上次观察及其时间，同时记录本次查询失败，不把故障推断成删章或撤稿。提交成功提示不足以证明全文核验或读者可见。

## 并发、改稿和中断恢复

准备时用一致的本地读取快照取得正式版本、审查收据和正文。执行前重新核对所选章节 head、审查、目标绑定、授权和导出健康；发现变化，将清单标为 stale，重新生成和展示差异。即使正文 SHA 相同，正式 head 或审查证明变化也不能直接沿用旧批准。

发送前持久记录意图，并在本机对同一平台作品的写入串行化；互斥身份按平台、账号、远端作品 ID 确定，不能仅按书目录路径。取得平台作品执行锁后，与创作提交共用短时 `operation_lock`，在锁内完成最终正式版本／审查核对；同时通过发布账本事务及条件更新核对 prepared 状态、绑定版本和授权，检查取消是否已生效，并持久化发送意图及 sending 状态。更新失败不得发送。发布入口统一采用“平台作品执行锁 → 创作 operation_lock → 发布账本事务”的顺序，绑定变更和取消也须经过同一账本的条件更新，不能绕过状态约束。

durable sending（发送意图已经成功持久化）是本地分界点：此前发生的改稿、取消或绑定变化必须被最终核对拦截；此后使用固定快照，避免上传过程中读到一半新稿、一半旧稿。释放创作锁和账本事务后才执行网络操作；平台作品执行锁只用于串行化发布，不阻止正常写作。不承诺网络上传和本地改稿之间存在跨系统原子事务，分界点之后的本地改稿形成“本地有新版待同步”。之后请求取消须先核对发送阶段和远端结果，不能只将本地状态改成 cancelled。

网络请求和人工验证不长期占用创作数据库事务。已准备的清单可以暂停；一旦发生可能已经到达平台的写入，就必须先核对结果，不能当作尚未发送。

| 情形 | 必须采取的行为 |
|---|---|
| 提交后超时、进程退出、回执落盘失败 | 记录或恢复为 unknown，查远端后决定；不直接重发 |
| 只找到同名、同章号或同字数章节 | 作为疑似匹配；不能凭这些信息证明内容一致或直接覆盖 |
| 远端列表未加载完、分页不完整、全文不可读 | 保留证据范围；不能推断章节不存在或全文一致，未知结果不自动重复创建 |
| 从旧备份恢复或复制书根 | 每次执行前都对账；本地旧账本中“未发送”不证明远端未收到，保留恢复/实例信息 |
| 两台电脑同时操作同一作品 | 本机锁不足以协调；首版限定单执行端，无法确认独占时不宣称严格去重 |
| 本地已发章再次修订 | 建立更新既有远端章节的独立计划，保留原发布版本；不自动覆盖或新建重章 |
| 远端被人工修改 | 先显示本地与远端差异；不将远端改稿自动收录为本地正式稿，也不自动覆盖 |
| 平台拒绝、额度不足、验证码或身份不符 | 标记 blocked，停止依赖它的后续章，保留已成功部分；不切换账号或改写内容来强行通过 |
| 本地撤销或取消清单 | 未发送的可以取消；已保存草稿、已排期或已提交的，需另行执行并核实远端撤销，不能只改本地状态 |

远端缺少幂等键或可靠内容回查时，不能承诺“恰好发布一次”。首版遇到结果不明应交由人工核对；人工确认需保存证据和确认者，不伪造 full_match。远端同章已存在时，默认进入对账而非直接再次创建。

章序以数值排序，并检查所选范围及远端已有前序章。第 1 章尚未确认提交结果时，不继续自动发第 2 章；成功进入审核是否允许后续章提交，以平台规则为准。卷号、卷名、平台章节分组分别核对，不把本地路径直接当作平台目录。

定时发布优先使用已验证的原生排期能力，保存明确时区和平台确认的时间。排期已被平台接受后，由平台负责到时处理；本机是否在线不应作为到时执行的前提，但审核、撤销或平台限制仍可能影响上线。本地唤醒后自动点击发布属于另一项功能，本方案首版不包含该运行保障。

## 分阶段验收

| 阶段 | 完成范围 | 可以对用户声明 |
|---|---|---|
| A：离线准备 | 清单、固定快照、审查资格、路径/章序、独立账本和恢复规则；不接触平台 | 可以准备发布材料；尚不支持上传 |
| B0：人工交接核对 | 作者在官方后台自行填写；本地工具比较作者提供的草稿副本，可显式留存不含正文的比较摘要并找回历史 | 可以报告作者副本与本地清单是否一致，不能声明平台保存或账号绑定已验证 |
| B1：平台草稿 | 取得适用平台书面接入许可后，核对账号和作品，授权后单章存草稿、回读及恢复测试 | 仅对许可覆盖且实际验收的平台、入口和内容范围声明草稿上传能力 |
| C：提交与排期 | 明确授权的提交、原生排期、远端状态对账、异常恢复 | 区分提交、审核、排期与上线；报告具体已验证范围 |
| D：修订及短故事 | 已发布章更新、远端外改冲突、短故事整篇提交分别验收 | 每项通过后单独启用，不从长篇首发推定支持 |

番茄的公开定时发布资料只证明官方后台有相关功能，不授予第三方工具接入权限。两家自动化草稿、提交与排期均暂停在平台许可核验之前；B0 可独立推进，但作者提供的回读副本不能冒充工具直接读取的远端证据。确认前两家都不能在安装说明或版本说明中标成自动发布已支持。

开发阶段至少覆盖以下可重复测试：

- 原始导入稿被阻止执行，导入章完成有效历史审查后能通过资格检查。
- 清单准备后换 head、换审查、改正文、换账号或作品绑定，都不会默默沿用原授权发送。
- 在最终核对与持久化 sending 的间隙注入改稿、取消和换绑定，验证锁及条件更新防止失效清单发送；持久化后、网络开始前退出则按未决尝试恢复。
- 第一行正文不是章头时完整保留；中文标点、多段对白、CRLF、非 BMP 汉字可往返核对；第 2、10 章顺序正确。
- 模拟平台收到前失败、收到后回执丢失、发送进程退出三种情况；后两种进入待核实而不是重发。
- 远端列表分页、只回读片段、平台标准化正文分别返回准确核验范围；不产生假 full_match。
- 重复点击、两个本机进程、恢复旧账本、复制书根不能直接重放发送队列；跨设备并发限制有明确结果。
- 草稿、审核中、驳回、排期和读者可见分别记录；查询失败不覆盖最后一次确定状态。
- 排期时区、远端撤销、已发章本地修订与远端人工修改均不触发隐式覆盖；失败后只恢复未决部分。

模拟测试只验证发布模块的本地逻辑。真实后台验收另存平台、入口、操作时间、账号与作品的脱敏标识、固定内容摘要和回读证据，不在公开仓库提交小说全文、登录材料或敏感截图。macOS、Windows 的测试结果各自记录，不把本机浏览器验证视为跨平台通过。

当前源码只实现阶段 A 和 B0 的本地部分。[比较留痕与材料核验](../benchmarks/results/publish-preparation-2026-09-23/comparison-ledger/README.md)记录本轮三个留痕命令、ZIP 竞态修复、完整回归与独立试用。[人工交接与边界历史验证](../benchmarks/results/publish-preparation-2026-09-23/manual-handoff/README.md)、[回执找回与正文格式历史验证](../benchmarks/results/publish-preparation-2026-09-23/receipt-and-dialogue/README.md)、[材料包复核历史验证](../benchmarks/results/publish-preparation-2026-09-22/archive-verification/README.md)及[材料导出阶段验证](../benchmarks/results/publish-preparation-2026-09-22/material-export/README.md)保留各阶段的代码快照。上面的网络、sending 竞态、平台草稿上传、正式发布及排期验收尚未执行，不能由本地准备测试推定通过。
