此记录区分已观察事实、根因、修复、验证和未解决事项。不得把模型验证、工具启动或本地预览单独视为 Chrome 连接成功；不得把只读检查视为草稿已保存。每次执行的脱敏连接里程碑保存在对应的 `~/.story-skill/chrome-workers/<执行编号>/diagnostics.json`；平台章节变更与回读记录以作品自己的草稿日志为准。记录不保存正文、账号、凭据或原始错误文本。

## 2026-11-04：浏览器执行工具找不到或调用失败

- 成功对照：10:31 的 Windows 会话记录显示模型核验、工具启动、桥接就绪及正常结束；该记录只证明当时连接链路可用。
- 现象：14:32 和 14:37 的新会话通过模型核验，但工具发现失败。工作台 v9 和 v10 的浏览器执行核心文件摘要一致。
- 已确认的原因：本机 Codex 配置指向不存在的旧 `node_repl.exe`、Node 和模块目录；当前安装目录包含对应文件。新运行环境目录约 13:46 出现，v10 约 14:29 才安装。旧目录为何消失尚无直接证据。
- 已执行修复：备份配置后，仅更新上述三个启动路径，其他解析后的配置不变。使用当前配置对工具进行本地只读初始化和工具列表检查，`js` 接口可发现。
- 修复后验证：对一部作品的第 86—135 章启动只读差异检查，模型 `gpt-6.1-terra` 已核验、工具已启动，但工具调用失败；0/50 章完成，未连接 Chrome，未写入平台。故路径修复有效地恢复了工具发现，但完整连接尚未修复。
- 尚未确认：本次工具调用失败的原始原因未被旧版诊断分类记录，不能断言与路径变更、信任设置或浏览器授权的关系。不得通过更改授权、伪造会话身份或重放写入绕过。
- 版本与复发对比：10:31 成功使用 v9；14:32 首次观察到工具发现失败时使用 v10。根据已冻结的两个候选清单，执行核心三个文件摘要一致，变化文件为 `story_publish.py`、`story_workbench.py` 和 `story_platform_drafts.py`。工具目录变化在 v10 安装之前，不能据此认定 v10 导致旧目录失效。
- 既往记录查询（截至本次本机扫描）：工具发现失败至少出现 4 次，最早记录文件更新于 14:32；工具调用失败至少出现 2 次，最早记录文件更新于 14:46；此前的宿主拒绝浏览器访问至少出现 3 次，最早记录文件更新于 11 月 3 日 22:47。文件更新时间不一定是故障发生时刻。以上仅覆盖仍存在的本地诊断，不代表全量历史；错误码重复也不证明底层根因相同。
- 后续处理：开发中的诊断保留脱敏错误结构指纹、错误来源、工具状态、数值错误码及连接阶段里程碑；根据新的实际证据确定原因后记录具体修复。结构指纹只反映错误结构，不能证明根因相同。完整验收须在 Windows 上完成真实只读差异检查，并确认执行会话正常结束。
- 补充本地验证：以当前配置启动工具并执行不接触浏览器的基本 JavaScript，返回成功；`@oai/sky` 和已安装的工作台执行模块也能加载。这些只证明基本执行和模块加载，不代表工作台会话或 Chrome 授权可用。
- 插件检查：Codex 本地配置中的 Chrome、浏览器及计算机使用插件均显示启用，Chrome 插件目录存在。10:31 成功会话与修复路径后失败会话的记录均指向 Chrome 插件 `26.1027.30824`，该 SDK 文件现存；这不能证明其他宿主运行环境未变化。启用状态不能证明插件在当前执行会话内可用、Chrome 已连接或宿主已经授权。
