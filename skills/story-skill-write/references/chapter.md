# 正文单元的写作与提交

本流程用于正式托管的正文单元。起草前读取 [冲突、看点与中文场景](drama.md)，同版已在上下文中则复用；新书首章重点核对开篇切入，多章连载核对跨章推进，高潮章核对阶段兑现，章末核对钩子承诺与下章回应，按本次任务取用对应段落。使用共享 `<tool>`；下列所有书籍命令均附加 `--book "<书目录绝对路径>"`。本章计划和授权范围已确定后执行。

## 章幅与计数

新写的完整章节正文须在 2400—2800 字内，短篇按章交付同样执行。默认章计划为 `length: [2400, 2800]`、`count_method: visible_nonspace_v2`、`count_title: false`。v2 统计独立可见字符，含标点，排除普通空白、控制／格式字符、附着标记及已识别的空白外观填充符。

默认不计首行章名，兼容识别旧稿 Markdown H1；`count_title: true` 时计标题文字，H1 开头的 `#` 和可选尾部闭合标记不计，标题内容中的 `C#` 等实际文字仍计。导语属于正文，作者有话说、创作过程说明和审稿意见不混入正文，也不计入正文章幅；作者有话说按下节另存，不把带有它的合并文本交给正文计数工具。`visible_nonspace_v1` 沿用旧可见字符口径；`letters_numbers_v1` 只计 Unicode 字母与数字，中文／英文均逐字符；`han_v1` 只计 Unicode 已命名汉字及〇。各口径排除普通空白和控制／格式字符；使用其他口径的新稿仍以 v2 交叉核验最低字数，不用附着标记或填充符垫数。旧章保持历史计数，不追溯重算。

起草或已授权整章修订前核对本轮要求、现行 `创作约定.md` 与计划；旧范围只是先前默认值时，先同步相关计划和可读细纲。用户或书根约定明确要求其他范围、口径或标题计数时，在计划中按 [章幅例外依据](../../story-skill/references/project-state.md#状态卡与工具章计划) 留存真实来源与原句，再按约定核验；单改 `plan.length` 不能使无依据例外生效。已提交旧章、章中续写及局部修改不因新章要求自动扩写。

上述计划同步与例外登记用于本次已获准写入正式规划或正文状态的流程。仅交完整章候选时，按本轮明确要求或现行约定确定篇幅、口径和章名计数，直接实测，以本轮原话或已有约定作为真实例外依据；没有明确例外仍遵守默认章幅。不为候选初始化书库、补建或改写已采用章计划，也不另建例外表单。后来获准采用时，再将真实例外登记到对应章计划，并按正式提交或修订流程重新核对细纲、篇幅与稿件。

按所选口径报告实测数，不冒称平台后台字数。欠字只补足已授权且对人物选择、回应、感受或后果有作用的内容，超字压缩冗余；不展开无新作用的账目或流程凑字数，不补造情节。

## 作者有话说的保存与核验

按 [作者有话说](drama.md#作者有话说) 确定本次须自动配写或复核附言及配图的章节；短故事／短篇默认跳过本节，不补写、不建附言文件或配图目录，也不把缺少它们列为交付缺口。用户明确要求时只处理指定范围。下述补齐要求仅适用于该范围，不因返回整章文件或全文而把局部校对扩大为整章内容改稿。当前 `lint`、`prepare`、`commit` 用于纯正文草稿，不会识别或扣除末尾附言；传入的 `.md` 仍只含章名与正文，不能把作者有话说或图片引用塞进正文、摘要、状态卡或审查引文。

正文定稿后自动准备本章附言和配图。正式章节提交前，先在 `.story/drafts/` 保存与最终草稿对应的 `<草稿名>.作者有话说.md`；正文成功提交并导出后，将已核对的配套文本保存到本书既有作者附言目录，没有约定时使用 `作者有话说/<卷目录>/第N章 章节名称.md`。卷名、章号与章名取本章实际导出结果，旧路径作品按已核对的卷章信息建立对应，不迁移原正文。草稿与随章附言文件统一使用 UTF-8 编码的 `.md` 格式，文件内只写附言文字及实际配图的 Markdown 引用，不添加“作者有话说”标题、章名或其他标签；用户免除配图或配图尚未完成时先保存文字，不插入占位链接。已有文件先读并保留旧版，不覆盖作者的未核对修改。仅交候选时，附言与候选同放非托管位置，不提前写入正式配套目录；只在对话交稿时无需另建附言文件，仍须展示实际配图。

每章默认交付一张实际配图：已有本章配图先复核是否仍适用，没有合格图片时自动调用可用的图像生成或编辑工具，不以“本章不需要”为由省略。落盘交付时，最终图片保存到对应附言文件旁的 `配图/` 子目录，按章号命名并保留已有版本；候选图随候选附言保存，正式交付时一起复制并更新引用。`.md` 中用 Markdown 图片语法和相对路径引用真实图片，便于整套移动；在对话展示本地图片时按宿主要求使用绝对路径。附言中的图片引用是允许的格式，小说正文仍遵守纯文本规则。

交付前逐章核对正文与附言的非空内容、章号对应、正文末段和附言的语义一致性，并实际查看配图，核对画面、章号和人物设定。落盘交付时打开实际正文与附言文件，确认 `.md` 引用解析到可打开的文件，一起交付正文、附言和图片路径；纯对话交稿则核对当前章正文、附言文本与实际图片，无需另建文件。两种方式均在本章完成回复中展示附言和配图，不以提示词或空链接代替成图。工具不可用或生成失败时说明配图未完成，已完成的正文和附言照常交付，不把缺图章节称为配套齐全；用户明确免除的项目按其要求处理。图片与引用不计入正文字数，不进入剧情状态、正文审查引文或短篇正文合并。正文修订或改名时复核本章附言、配图及对应路径，保留仍适用的内容，不因正文更新而沿用失效评论或图片。附言与配图是独立配套文件，`status`、`export` 和提交回执不验证或恢复它们；须另行核对后再报告该章交付完整。短篇合并文件仍只含各章章名和正文；只有用户明确要求时，完本交付才另行核对、交付指定范围的附言及配图，不直接改受保护的全文导出。

## 正式章节流程

已按 [已采用细纲绑定](../../story-skill/references/project-state.md#已采用细纲绑定) 登记的章节，`context` 会校验可读细纲与工具计划的具体版本；版本漂移时先审阅并同步，再重新绑定。返回 `outline.status=unbound` 时仍要定点核对细纲，不能把未绑定误报为一致。首次正式提交新章前必须完成绑定，再取得新的 context 与审查凭据；缺绑定会被 commit 拒绝，旧书续写的新章同样适用。候选审读及已提交旧章的兼容路径不自动补绑定。

1. `context --book "<目录>" --chapter N --budget-bytes 16000`。它完整保留本章工具计划、匹配范围的 critical 卡和到期承诺、requires 卡及上章摘要/末尾；已绑定细纲仅校验文件摘要，不返回细纲内容或判断语义一致。定点读取本章已有细纲及采用依据，与返回计划核对；不一致时按 [项目状态](../../story-skill/references/project-state.md) 同步已采用内容，再重新取得 context，不用候选覆盖现行计划。进入新卷时还须回读前卷结束条件和有关正文：若条件未达成，按授权说明推迟或修订卷纲，并让跨卷行动承接这一缺口，不能以新卷目录替代前卷回报。核对本章所需硬限制卡已在 required_cards 中；`volume_dir` 不建立 scope 关联，缺卡先修正对应稳定 ID 或 requires。预算是 UTF-8 字节，不是假称的模型 token；仅不相关的可选卡可被省略。过期/已完成伏笔也可按 requires 显式召回。查历史原因用 `recall --query "<人名或线索>"`，必要时读取精确原文。
2. 在 `.story/drafts/` 起草前按 [主要人物定义与核对](drama.md#主要人物定义与核对) 定点核对本章关键人物及当前状态，并按 [叙述视角与场景转接](drama.md#叙述视角与场景转接) 核对有关约定和衔接，再按已读场景指导展开章计划，并按 [场景展开与情绪层次](drama.md#场景展开与情绪层次) 展开值得读者停留的选择、交流或体验，不把完成计划节点当作场面已经写足。保留本书声线与有功能的安静，不提前用尽终局底牌。起草前对照近期章节；若主要场景反复是核对条件、比对材料或登记结论，且没有带来新的取舍、关系或实际后果，先在授权范围内调整计划，不靠流程填足篇幅。衔接不清时定点补读原文。核对章名及所属卷的完整 `第X卷 卷名` 目录；完整章节沿用已确定的章号与章名，草稿首行使用纯文本 `第N章 章节名称`；正文依 [成稿格式](drama.md#成稿格式) 按语义分段，普通段间空一行，不手工缩进或插入装饰分隔线；[对白分段](drama.md#对白分段与说话人)以发言和说话人归属为准。同一人物紧密动作与短对白可同段。正文不添加 Markdown 的 `#` 标题、加粗、列表、引用、链接或代码围栏语法；作品本身需要的专用符号仍按原意保留。文件仍为 `.md`，章计划 `title` / `volume_dir` 的取值规则见 [项目状态](../../story-skill/references/project-state.md)。
3. `lint --chapter N --draft "<草稿>"` 检查计划中的章名与分卷导出路径、[篇幅及例外依据](#章幅与计数)、损坏字符、占位符和重复行。新完整章的首行须是纯文本 `第N章 章节名称`，章号、章名与计划一致；旧章原有的无章头或 Markdown 章头仅在首行和计划章名均未改时兼容，新改的首行须符合现行规则。`prepare`、提交和历史发布也核对章头。`lint` 另在 warnings 中给出部分半角点号、省略号及破折号形态疑点，带原稿行列和片段，须按 [小说标点校对](punctuation.md#工具提示与交付复核) 逐处复核；提示不自动改稿、不影响脚本 ok。正文的工作材料、Markdown 标记、空行、对白归属、句号位置、引号层级及标点语义仍须按 [成稿格式及校对](drama.md#成稿格式) 通读，不能据脚本通过或零警告报告格式与语义已通过。
4. 先按 [正文内容审查](content-review.md) 读完本章与必要衔接，形成因果、连续性、约束与读感的真实结论；对照本章计划与明确阅读承诺，保留支持、反证及未解决问题。首章、中途章、高潮章按各自阶段复核，不逐场套同一构思公式。若字数与事实检查通过而读感仍平，如实保留该意见，不称质量通过。同时按 [随章保存与核验](#作者有话说的保存与核验) 核对本章附言及配图；正文提交与配套材料齐全分别确认。
5. `prepare --chapter N --draft "<草稿>"` 返回 lint 与绑定书籍、状态版本、稿件哈希的 delta 骨架；将其中 `delta` 另存文件，再依据第 4 步结论填写摘要、changes 和因果／连续性／用户约束／文风四项观察与最终稿原句，处理问题清单。四项和引文只是提交凭据的结构门槛，不能代替实际通读。骨架含待审阻断项，不能直接提交；`blocker` 未解决不能提交，普通建议可说明取舍。changes 仅记正文实际发生的变化，引文必须来自最终草稿；审查后稿件改变时重读受影响内容并重新取得骨架，不只更新哈希。
6. `commit --chapter N --draft "<草稿>" --input "<delta.json>"`。正文、审查凭据、增量状态在同一 SQLite 事务中保存；随后按分卷导出为 `chapters/第X卷 卷名/第N章 章节名称.md`，N 不补零，使用回执给出的实际路径交付。已有章的旧导出路径不自动批量迁移。重复同一提交不会推进两次。版本冲突先刷新上下文并复核，不能只改 revision 数字重试。导出失败运行 `export` 恢复，不能把未导出的章说成交付完成。交付前打开实际导出文件，核对章名、授权范围、正文完整性、段落和标点，与最终稿一致；已提交章若仍需去格式，转审稿修订流程，不直接改托管导出文件。成功导出后，若现行可读总纲、卷纲或细纲写了明确的提交进度，只更新涉及本次章节的状态句并对照 `status`，不把尚未兑现的卷目标标成完成；纯进度更新无需另存每章的大纲历史副本，但被绑定文件的任何字节变化都须按 [已采用细纲绑定](../../story-skill/references/project-state.md#已采用细纲绑定) 复核并重绑该文件的全部关联章，再取得下一章 context；规划本来未记录进度时，可把进度留在未绑定的进度入口。实质规划变更仍按 [项目状态](../../story-skill/references/project-state.md#已采用规划的联动) 归档并联动。外部改稿冲突转 [审稿修订](../../story-skill-review/SKILL.md) 的 reconcile。

提交后为下一章保存状态时，先看它是否依赖本章较早出现的关键原话、物件归属、人物知情或期限；`previous.tail` 与摘要未覆盖的关键内容，应定点回读正式正文，并在确需跨章召回时保存简短有来源的卡片、加入下一章 `requires`。不把每个观察都记成卡片，也不把卡片代替原文。

## 全书完本审查

写到本书实际终章并准备报告完本，或本次明确要求整书完本审查时，长篇与短篇都核对已采用总纲、开篇建立的主要阅读承诺和实际结局。以本次待交付稿为准，用目录、摘要和状态记录定位，再回读有关原文：核心冲突如何经由人物的关键选择走到结果，主要关系与代价的后果是否呈现，重点承诺与伏笔是否已兑现，或有作品内的依据说明其转变、放弃。

本书已有已采用的核心追问、关系关注或叙述取舍时，沿 [生活观察与核心追问](drama.md#生活观察与核心追问) 和 [作品的观看方式](drama.md#作品的观看方式) 定点回读相关关键场面与结局：这些关注怎样通过人物选择、他人回应、细节取舍与前后后果具体成立，是否只由结论式解释宣布。规划中的表达意图不能作正文证据；没有明确这些关注时不强行补主题或品质表。判断沿用 [正文内容审查](content-review.md#结论反证与未决问题) 的问题分类与实际阅读范围，不增加品质评分或完本凭据字段。

区分本书已收束的事项、有意开放的问题与续作引子；开放结尾可以留未知，不要求交代所有人物的余生，也不能用续作悬念遮住本书主线的缺口。此处核对结构性收束及本书已有创作关注的实际呈现，不代替逐章全量读感审查；结论沿用本次审稿记录，指出依据、实际回读范围和未解决项。缺原文或结局尚未成稿时说明未核范围，不凭大纲、状态标记或单章通过报告全书完本。普通中途章节或局部校对不自动扩成全书审查。

本次完整目标已包含整书优化、终稿打磨或整部成稿的质量提升时，继续按 [整书改稿与终稿打磨](content-review.md#整书改稿与终稿打磨) 完成实际全文阅读、必要修订与改后复查，再交付约定终稿；普通完本不自动增加该流程。章节齐全、结构收束和整体读感的实际审查范围分别说明，不能用其中一项替其余项作完成声明。

## 短篇完本与修订交付

短故事／短篇完本不要求“作者有话说”及其配图，默认只按本次流程交付正文、全文、封面和适用规划；已有附言与图片保留，用户明确要求时另行处理。

完整短篇交付时，无论新写还是修订后成品，都按下述共享规则核对现行总纲或等效规划的分类覆盖：默认番茄、七猫均有独立完整分段，本次要求或书内约定涉及的其他平台也列全，不因主投平台省略另一套；用户明确限定本轮单平台时，只核对和交付该平台分类。先核对并在交付说明中列出共用的主角与关键人物角色定位，再逐平台核对本书篇幅类型、实际入口、原生栏目与分类、正文依据、来源日期及拟选／已确认／待核对状态；分类答复也按同一范围给齐，并按 [平台作者名与署名](../../story-skill/references/project-state.md#平台作者名与署名) 逐平台列明作者署名及其依据、状态，不混用各平台署名。人物标识留在规划与交付说明，正式正文按场景呈现。缺文件、缺项或与终稿不符时，按 [大纲的平台分类字段](../../story-skill/references/project-state.md#大纲中的作品类型与平台分类) 留存已有旧版并补齐或更新；已有平台确认值保持实际记录，差异和未核实选项明示待核对，不把本地拟选改称后台已确认。此项在完本交付时核对，不为每章重复查询平台。交付列出全文、实际封面和现行总纲／等效规划的路径，以及剩余待核对项。

短篇同样放入带卷名的首卷目录，可整篇作为第 1 单元，也可按用户要求分单元提交；范围对应当前单元。用户直接要求“不分章”或“整篇一次写成”，并指定整篇字数，即可作为整篇一单元的真实篇幅例外依据，无需再用工具术语确认。其他整篇一单元例外沿用用户要求或书根 `创作约定.md` 的真实依据；正式写作前把实际范围写入该单元 `plan.length`、把依据原句写入 `plan.length_exception`，候选交付按 [章幅与计数](#章幅与计数) 处理。分章短篇只给全书总字数不取消每章 2400—2800 字的默认约定；没有整篇例外时按有意义的叙事节点分章，不为凑字数机械切断场景。既有正文不因这项规则追溯扩写。

接入的旧短篇先按 [补齐原章流程](../../story-skill/references/project-state.md#旧短篇补齐原章) 核对并补存缺失原章。全书完本并完成逐章导出后，执行 `assemble-short --book "<目录>" --final-chapter N`，N 为本书实际最终章号；工具核对章节与导出，在书根新建全文并登记为受保护导出，逐章 `.md` 保留。普通书名使用 `<书名>.md`，特殊或过长书名使用回执中的合法文件名；完整书名保留在书籍信息中，预期与登记路径见 [书名与路径规则](../../story-skill/references/project-state.md#书名目录与开书落点)。新合并稿从第 1 章章名开始，按章号顺序仅包含各章章名和正文；旧版含书名首行的合并稿须重新合并并保留备份。核对章节完整、总长度、段落及导语没有重复，打开实际全文文件检查，再按 [全书完本审查](#全书完本审查) 核对文学收束并交付实际路径。

已有全文在正式章节修订、对账、历史发布或新增章节后随导出刷新，包含当前全部连续已提交章节。交付前核对 `status` 的 `short_assembly`、导出回执及实际全文；缺失或待导出时运行 `export` 恢复，全文外改时先把该文件移到 `.story/drafts/` 等非托管路径保留，再运行 `export` 恢复已提交版本；需要采用的改动逐章审查后提交，不直接用全文覆盖章节，也不把全文交给仅处理章节的 `reconcile`。`short_assembly` 仅说明同步状态和已合并章数；后续新增章节不受原终章号限制，是否完本仍须按实际终章、结局与全文核对。仅审稿或未采用的候选修改不刷新正式产物；单章要求不扩成全书，也不自动生成首次完本文件。

首次短篇完本合并通过后，读取 [封面技能](../../story-skill-cover/SKILL.md)，依据最终作品及本次目标平台的署名、规格核对或制作封面；已有对应合格封面可直接沿用。只制作本次要求的版本，分类覆盖多个平台不自动增加封面数量；署名或规格不同的版本分开保存并保留旧版，已核实可共用时可复用。把可打开的图片保存到本书目录，核对中文书名、对应平台的作者署名和实际尺寸，与全文一起交付实际路径并说明适用平台或本地用途。缺署名不自拟，也不借用另一平台的署名。后续正式修订仅在书名、署名、题材或投稿规格变化时复核并按需修订封面，不因普通文字校对重复制图。只交提示词或方案不算完成完本交付；没有生成能力时如实报告封面仍未完成。不为中途单章自动制作封面。

## 多章连载

多章连载按近期摘要和当前承诺，依 [主线跨章推进](drama.md#主线怎样跨章前进) 核对本章是否承接先前选择、阻力和解法是否重复；工作记录不为下一章自动生成同类情节。对手根据已知事件调整，旧办法留下后果；升级可改变合作条件、关系或责任。阶段所得要实际体验并影响后续，安静章容纳余波。摘要不够判断时定点补读原文，不把同一轮拖延或强塞新危机当推进。更新近期细纲、阶段关键选择落地或目标转向时，依同一参考中的阶段回看核对正文积累与完成条件，再安排后续。明确多章请求按章循环到授权范围完成。

写到已安排的高潮章时，按 [高潮与阶段兑现](drama.md#高潮与阶段兑现) 回看铺垫、正面碰撞、选择、结果和余波是否在正文中成立；不要只写到冲突将起便停章，也不要把关键胜负留给下一章的事后转述。高潮可以跨章，但前一章也要有实际攻守或处境变化，最终胜负在已规划的节点兑现。若本次授权只到高潮前的局部片段，按原停笔范围处理，不借这条擅自续写。
