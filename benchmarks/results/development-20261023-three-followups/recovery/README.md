# 恢复中心分页修复验证

本目录记录恢复中心的开发版修复；只使用隔离合成作品，没有修改真实作品、同步安装或发布。

## 原问题与红例

- 编辑页恢复中心只读取材料目录首批 5000 个节点，忽略未完成标记，可能把磁盘上存在的恢复稿报告为“没有记录”。
- 书架恢复中心仍调用旧全材料扫描，检查第 5001 个节点时整书恢复列表失败；原有 100 条截断也没有后续页面入口。
- `prior-bug-probe.py` / `prior-bug-result.json` 保留修复前的独立复现：5001 个历史材料，恢复稿由生产 `_editor_save(..., recovery=True)` 生成，下一批和直接打开均可读，但旧恢复 UI 误报空态、旧书架报 `workbench_scan_limit`。这个脚本的断言针对修复前行为，不作为修复后通过脚本。
- `red.log`：最先新增的 9 条回归在修复前为 1 通过、1 断言失败、7 错误；其中真实大目录用例直接触发原扫描上限，分页契约和共用 UI 尚不存在。随后补入两条书架懒加载验证。

## 实现契约

两个入口共用 `story_workbench_archives.recovery_catalog`，复用既有目录句柄和作品身份绑定的安全材料扫描器。恢复扫描仅保留恢复类行，并按稳定发现顺序追加。材料目录原有排序不变，两种扫描模式不能串用游标。

- 编辑页：`api/recoveries` 接受 `cursor`、`offset`，直接返回恢复分页包。
- 书架：`/api/recoveries` 未指定 `key` 时只列作品，不创建扫描游标；选定作品后接受 `key`、`cursor`、`offset`，在 `books[0]` 返回同一分页包。选择页显示类型与可区分同名书的目录。
- 每个结果页最多 100 条。分页包包含 `cursor`、`offset`、`next_offset`、`has_more`、`complete`、`scan`、`warnings`；`count` 是已经发现的数量。后续请求使用 `cursor` 和 `next_offset`。
- 先读完已发现的结果页，再推进下一批扫描；无恢复项的扫描批次可以返回相同 `next_offset` 和 `has_more=true`。后续发现修改时间更晚的记录不会移动已有结果的位置。
- 两端共用“继续加载恢复记录”和“重新读取恢复记录”。只有完整扫描、无扫描警告且结果为空时才显示空态；异常或过期保留已列记录，重新读取使用新游标。关闭或更换对话框后的迟到响应不更新新界面。
- 原有每批 5000 节点、总计 100000 节点、600 秒游标寿命和最多 8 个扫描会话边界保留；达到总上限明确提示未完成，指定文件仍可按既有安全规则直接打开。
- 来源元数据、内容类型、章号导航、待核对保存记录及直接打开的验证沿用原实现；列表不表示正式采用。
